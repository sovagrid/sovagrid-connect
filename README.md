# SovaGrid Connect для компьютера

Настольный коннектор открывает **полную веб-панель SovaGrid** в обычном браузере через SSH по пути `/sovagrid/monitoring/`. Он запускает локальный проброс только на `127.0.0.1`, дожидается подтверждения OpenSSH о привязке именно этого порта, проверяет ответы `/healthz` и страницы панели, затем открывает браузер. Уже занятый локальный порт отклоняется. Порт `8766` сервера не требуется публиковать в интернете.

Работает с системным OpenSSH на macOS, Linux и Windows и Python 3.9+. Дополнительных Python-библиотек нет. На macOS выполнены тесты с OpenSSH 10.3p1 и Python 3.9/3.15, и локальный проброс к тестовой панели. На Ubuntu 26.04 семь тестов прошли от непривилегированного пользователя. GitHub Actions проверяет Python 3.9 и 3.13 на Windows/macOS, Python 3.9 на Ubuntu 24.04 и Python 3.13 на Ubuntu 26.04. GUI на Windows пока не проверен вручную.

Внизу окна Connect есть выбор **Системная / Светлая / Тёмная**. Системная тема использует оформление Tk и ОС; две явные темы перекрашивают элементы Connect, включая поля списка служб. Выбор хранится локально в пользовательских настройках Connect, без ключей и паролей. Системные диалоги выбора файла, SSH-пароля и подтверждений оформляет сама ОС.

## Автономные сборки

GitHub Actions workflow собирает три исполняемых файла PyInstaller для Windows, macOS и Ubuntu 24.04: `SovaGrid-Connect-CLI`, `SovaGrid-Connect-GUI` и внутренний `SovaGrid-Connect-Askpass` для защищённых SSH-запросов в GUI. Askpass упакован внутрь папки GUI; на macOS он также находится внутри `.app`. В успешном запуске CI откройте **Artifacts** и скачайте архив своей ОС и архитектуры. Распакуйте папку GUI целиком либо откройте `.app` на macOS. Установка Python не нужна, но нужен системный OpenSSH. В архив включена короткая инструкция `dist/README.md`.

Сборка не содержит пользовательских SSH-ключей, паролей и конфигурации: CI упаковывает только код приложения и его Python/Tk зависимости. Архивы сохраняются как артефакты GitHub Actions на 14 дней; проверенные предварительные выпуски публикуются в Releases. CI проверяет `--help` у CLI и GUI, включая `.app` на macOS, и передачу тестовой строки через stdout Askpass. Linux runner не открывает окно в среде без дисплея, поэтому это не тест графического взаимодействия. На Windows и macOS сборки пока не подписаны; система может потребовать обычное разрешение для локально собранного приложения. Linux-сборка зависит от совместимости системных библиотек с Ubuntu runner.

Для передачи человеку одного ZIP на ОС используйте `tools/build_starter_kits.py`. Входной каталог должен содержать три архива успешного Connect CI (`SovaGrid-Connect-macOS-arm64.zip`, `SovaGrid-Connect-Windows-X64.zip`, `SovaGrid-Connect-Linux-X64.zip`) и доверенный `SovaGrid-server-source.tar.gz`, созданный из пяти серверных репозиториев. Скрипт проверяет манифест пакета и создаёт `SovaGrid-Starter-*.zip` с GUI, пакетом и короткой инструкцией:

```sh
python3 tools/build_starter_kits.py /path/to/input --output-dir /path/to/ready
```

Если `--output-dir` не указан, готовые ZIP кладутся во входной каталог. Пересоберите их после каждого изменения серверного пакета или Connect CI; внутри инструкции фиксируется SHA-256 вложенного пакета. На macOS сохраняются структура `.app`, права и символьные ссылки, на Linux — право запуска.

## Быстрый запуск

Из папки `sovagrid-connect`:

```sh
python3 -m sovagrid_connect connect --host server.example.com --user root
```

На Windows в PowerShell:

```powershell
py -3 -m sovagrid_connect connect --host server.example.com --user root
```

Программа запустит OpenSSH. Он сам попросит пароль SSH-пользователя или кодовую фразу ключа в терминале, если они нужны. После проверки панели откроется браузер с адресом вида `http://127.0.0.1:49152/`. В самой панели потребуется **отдельный** логин и пароль Hub. Оставьте терминал открытым; `Ctrl+C` закрывает туннель. Чтобы видеть адрес без автоматического открытия браузера, добавьте `--no-browser`.

Для входа с ключом:

```sh
python3 -m sovagrid_connect connect \
  --host server.example.com --user operator --identity ~/.ssh/id_ed25519
```

Локальный порт выбирается автоматически. `--local-port 8766` задаёт его явно. `--remote-port` меняет порт панели **на целевом сервере**; стандартное значение `8766`.

## Сервер через промежуточный узел

Если на промежуточном узле доступен обратный SSH-туннель целевого сервера на `127.0.0.1:22022`, этот маршрут работает через `ProxyJump`:

```sh
python3 -m sovagrid_connect connect \
  --host 127.0.0.1 --port 22022 --user targetuser \
  --jump-host server.example.com --jump-user jumpuser
```

Здесь целевой `127.0.0.1:22022` находится **со стороны промежуточного узла**, а не на вашем компьютере. На целевом сервере веб-панель должна слушать `127.0.0.1:8766` либо порт, указанный в `--remote-port`. Для разных ключей можно добавить `--identity PATH` и `--jump-identity PATH`. Если через разные промежуточные узлы есть несколько целей с одинаковым адресом `127.0.0.1:22022`, задайте каждой своё `--host-key-alias NAME` и заранее закрепите соответствующий ключ под этим именем в `known_hosts`. Для ключа самого перехода доступен `--jump-host-key-alias NAME`. Сам обратный туннель создаётся на стороне целевого сервера; коннектор его не настраивает.

## Графический запуск

```sh
python3 -m sovagrid_connect gui
```

На Windows замените `python3` на `py -3`. Tkinter должен быть установлен вместе с Python; в некоторых дистрибутивах Linux это отдельный системный пакет. В форме доступны прямой сервер, промежуточный хост, отдельные приватные ключи и локальный порт. Ключи выбираются через кнопку «Выбрать…»; путь к ним можно также вставить в поле. GUI показывает отдельные окна для SSH-пароля, парольной фразы ключа, кода 2FA и подтверждения нового ключа сервера. Перед открытием панели Connect по SSH отличает управляемую установку от пустого Ubuntu-сервера и от узла с одним удалённым Agent. На пустом сервере под `root` он предлагает установить и сразу открыть панель: проверенный пакет рядом с приложением используется без сети, иначе Connect скачивает закреплённый выпуск `v0.10.0-preview` с GitHub в закрытый временный файл, сверяет SHA-256 и структуру до передачи по SSH. В отдельном окне первой установки можно выбрать собственный архив; Connect прямо обозначает, что его происхождение не закреплено в приложении. На узле с Agent обычная первая установка закрыта; для него есть отдельный мастер собственного Hub. Частичная или нераспознанная установка автоматически не продолжается. Установщик отдельно повторяет проверку перед записью файлов. На новом Hub при SSH-входе с root/sudo правом Connect получает одноразовый 60-секундный пропуск и открывает местную панель без второго пароля. Пропуск передаётся из SSH в браузер через закрывающийся локальный посредник: в URL находится только его порт, а не пропуск; после входа посредник удаляет его из памяти. Если Hub ещё не обновлён или SSH не даёт административных прав, обычная форма местного Hub остаётся доступной. Старый путь «Получить начальный пароль по SSH» сохранён для совместимости, но файл `/etc/sovagrid/admin-password` устаревает после изменения пароля. Для исходного запуска GUI на Windows нужен собранный `SovaGrid-Connect-Askpass` внутри `dist/SovaGrid-Connect-GUI/`; готовый архив уже содержит его.

Для закреплённого выпуска 0.10.0-preview SHA-256 архива — `275c5f03c30b1a924b1fcb48067a41f7b76481cd4c249589a7c8b5098db749fb`, SHA-256 `sovagrid-bundle.json` — `2314f9b66ca1d70dba1e348ceb93e99367c5a074ceb370dc307f0dab4a877a03`. Манифест связывает пакет с точными коммитами:

| Компонент | Коммит |
| --- | --- |
| Blueprint | `e82e031a32da99a15740c1c0b22041c02f46f4a3` |
| Hub | `e40d1bcf8ae8d527ac9169d894a01bdf3f55ee71` |
| Agent | `5e2eea6c0f321c2cf0402737ba6b1fa369960d4c` |
| Web | `a02636b0cef2d2f91a3fec01fe941d4a77f62102` |
| VPN | `20ca2fa2bbe0f4747adfc2352e27da802882bdc6` |

Кнопка **«Из SSH config…»** возле адреса сервера показывает именованные `Host` из локального `~/.ssh/config`; можно выбрать другой файл. Перед заполнением формы Connect показывает адрес, пользователя, порт, ключ и переход, а также настройки, которые не будут перенесены. Поддерживаются `HostName`, `User`, `Port`, один `IdentityFile`, один `ProxyJump`, `HostKeyAlias`, обычные `Host`-маски и локальные `Include`. Несколько ключей, цепочка из нескольких переходов, `ProxyCommand`, `Match` и маршруты с `CanonicalizeHostname` требуют ручной настройки: кнопка применения для такого профиля недоступна. Другие директивы перечисляются в окне импорта, и перед применением требуется подтверждение. Connect **читает конфиг как текст**, не запускает `ssh -G`, `Match exec` или команды из конфига. После импорта поля можно проверить и исправить; дальнейшее подключение использует только собственный строгий временный SSH-конфиг Connect. Пользовательские пароли, ключи и токены не сохраняются в профиле Connect.

### Собственный Hub на сервере с внешним Agent

На Ubuntu-узле, где Agent уже подключён к другому Hub, нажмите **«Свой Hub на сервере с Agent…»**. Нужен проверенный SSH-вход `root` или пользователя с уже действующим `sudo -n` к самому узлу, в том числе через промежуточный узел с `ProxyJump`, и локальный `SovaGrid-server-source.tar.gz` из той же сборки, что и Connect. Мастер принимает только архив с закреплённым SHA-256 текущего кандидата. Он показывает точный SSH-маршрут, SHA-256 архива и манифеста и сначала читает состояние внешнего Agent без изменений. Перед установкой требуется отдельное подтверждение. Пароли SSH запрашиваются в окне OpenSSH; пароль sudo мастер не запрашивает и настройки sudoers не меняет. Токен Agent и сертификат CA не вводятся вручную.

После подтверждения мастер сохраняет root-only снимок внешнего Agent и обратного туннеля, передаёт проверенный пакет, запускает отдельный локальный Hub и подключает к нему второго Agent. Внешние Agent, его токен, CA, файлы, службу и туннель мастер сверяет на каждом этапе и сохраняет. При обрыве связи повторная проверка покажет подтверждённый этап и позволит продолжить с тем же пакетом. Изменение внешнего Agent, другой закреплённый пакет и частично установленный Hub блокируют автоматическое продолжение. Команды нового Agent остаются выключены.

Кнопка **«Проверить и открыть панель»** создаёт локальный SSH-проброс, проверяет `/healthz` и подтверждает метрику второго Agent не старше 180 секунд по времени ответа Hub, затем открывает браузер. Часы и часовой пояс телефона или компьютера на эту проверку не влияют. Публичный HTTPS для Hub-only узла настраивается отдельно; существующий маршрут через промежуточный узел должен уже работать. Секреты и вывод установки остаются в закрытых файлах на сервере; подробности протокола описаны в [Blueprint](https://github.com/sovagrid/sovagrid-blueprint/blob/main/PROMOTION.md).

### Обновление собственного локального Hub

Для Hub, добавленного рядом с внешним Agent, откройте **«Обновить собственный локальный Hub…»**. Мастер проверяет состояние установленной версии и точный локальный пакет текущей сборки, показывает SSH-маршрут, текущий и новый SHA-256, сверяет исходники на сервере и сохраняет кандидат в закрытом каталоге. До нажатия **«Применить обновление»** работающие службы не меняются. Перед применением удалённый helper повторно проверяет кандидат и текущую версию. Успех, отказ и результат отката показываются отдельно; внешний Agent и его туннель остаются под проверкой.

Отдельная кнопка **«Разрешить одно обновление при простое»** включает серверную политику для одного уже подготовленного пакета. Она позволяет серверу применить именно этот кандидат после закрытия Connect, когда Hub свободен. **«Состояние»** читает политику, а **«Снять разрешение»** удаляет её; системный timer может остаться включённым, но без разрешения ничего не применяет. Для первого перехода с версии 0.3.9 требуется ручное применение в мастере, после которого доступна серверная политика. SSH root или заранее настроенный `sudo -n` обязателен; пароли и токены в консоль вводить не нужно.

### Подписанный канал следующих серверных выпусков

Кнопка **«Подписанные обновления…»** проверяет по SSH точный установленный серверный код, systemd units, встроенные публичные ключи и текущую ревизию состояния. Если выпуск содержит доверенный ключ, после выбора ключа и отдельного подтверждения Connect может включить периодическую проверку подписанных выпусков. Сервер повторно сверяет ревизию под root-блокировкой; устаревшее подтверждение отклоняется. После включения или отключения Connect заново проверяет результат. Отключение канала не отменяет отдельное разрешение на один уже выбранный архив. Ключ подписи и токены в интерфейс или консоль вводить не требуется.

Если установленный выпуск больше не содержит ранее выбранный ключ, Connect покажет его как недоверенный и предложит только отключение канала после сверки ревизии. Новые подписанные выпуски в таком состоянии не принимаются.

Серверный выпуск 0.10.0-preview ещё не содержит рабочего встроенного ключа подписанного канала, поэтому включение на нём недоступно. Включение подписанного канала требует выпуска ключа и независимой проверки публикации.

### Терминал и файлы своего локального Hub

На сервере с уже созданным собственным Hub выберите **«Терминал и файлы своего Hub…»**. Мастер сначала сверяет точный серверный выпуск, SSH-маршрут, отдельный локальный Agent и сохранность внешнего Agent. После просмотра состояния терминал и файловая рабочая папка включаются и выключаются отдельно, с подтверждением каждого действия. Сервер сравнивает ревизию настроек под блокировкой; если их изменили параллельно, Connect требует новой проверки. После прерванной операции доступно отдельное восстановление прежних настроек. Это действие не открывает файлы внешнего Agent и не меняет его туннель.

Для этих функций команды второго, локального Agent должны быть **заранее разрешены**. Обычное создание собственного Hub оставляет их выключенными. Нажмите **«Разрешить команды своего Hub…»**: мастер отдельно проверит SSH-маршрут, точные исходники, состояние собственного Hub, локального и внешнего Agent, серверное разрешение команд и свежую метрику. После просмотра точного манифеста, ID Agent и ревизии подтвердите включение. Сервер повторит проверку под блокировкой, использует только свой проверенный помощник и затем подтвердит новое состояние. При изменившейся ревизии или неполном результате мастер остановится и потребует повторной проверки. Команды нельзя выключить этим мастером до появления отдельного проверенного серверного контракта. Токены, CA и пароль Hub в консоли не вводятся.

### Docker-мониторинг своего локального Hub

Кнопка **«Docker-мониторинг своего Hub…»** управляет отдельным сборщиком для локального Agent на целевом сервере. После проверки точного серверного пакета мастер показывает состояние таймера и свежесть снимка. Включение создаёт root-only сервис с доступом к Docker и сохраняет ограниченный снимок в отдельной папке, доступной только `sovagrid-local`; внешний Agent, его токены и туннель не меняются. Выключение удаляет локальный снимок и сервис. Оба действия требуют проверки ревизии и отдельного подтверждения. При потерянном SSH-ответе Connect не повторяет изменение автоматически: он читает состояние заново, а незавершённую операцию предлагает восстановить. Это включает только мониторинг; права `start/stop/restart` задаются отдельно в мастере действий с контейнерами. Для работы требуется установленный серверный пакет с закреплённым SHA-256; если он ещё не установлен, мастер показывает причину отказа.

После выключения действий с контейнерами мастер может удалить сохранённый список разрешений отдельной кнопкой. Он сверяет ревизию перед удалением и не затрагивает список другого Agent.

### Открыть панель с телефона по IP или домену

Нажмите **«Веб-доступ с телефона…»**. Мастер подключается к выбранному серверу через SSH, читает текущие настройки и показывает план перед включением HTTPS. Можно указать публичный IPv4 сервера или свой домен с DNS-записью A на этот IPv4, путь панели (по умолчанию `/sovagrid/monitoring/`) и поведение корня `/`: не занимать его маршрутом SovaGrid, показывать панель, перенаправлять на её путь или явно отдавать 404. Новая настройка по умолчанию не занимает корень; ранее сохранённое поведение сохраняется до выбора администратора. Порты 80 и 443 должны быть свободны и доступны извне. IPv6 и домены с AAAA в этой версии не поддерживаются.

После проверки нажмите «Включить HTTPS». Connect запросит доверенный сертификат Let's Encrypt и проверит публичный адрес. Продление выполняется автоматически на сервере. Первая страница предлагает вход по SSH с паролем или ключом, а также учётную запись панели; секреты не нужно вводить в консоли. Веб-панель по этому адресу позволяет нажать **«Сделать приложением»** и добавить SovaGrid на домашний экран. На iPhone открывается инструкция Safari, в поддерживаемом браузере Android или компьютера — системный запрос установки.

Сохранённый адрес и проверенная доступность показываются отдельно. После прерывания действия повторите проверку, прежде чем что-либо менять. Публичный HTTPS можно выключить в том же окне; SSH-доступ сохраняется. Для этого мастера нужен обновлённый серверный пакет; детали конфигурации описаны в [PUBLIC_WEB.md](https://github.com/sovagrid/sovagrid-blueprint/blob/main/PUBLIC_WEB.md).

### Функции уже подключённого удалённого Agent

В Connect 0.3.6 после подключения к Hub нажмите **«Функции другого сервера…»**. Войдите как администратор Hub, выберите зарегистрированный сервер из списка, его SSH-профиль и проверенный серверный пакет с этим мастером. Можно использовать прямой SSH или промежуточный узел с отдельными ключами. Нужен root либо пользователь с `sudo -n`.

Сначала мастер проверит, что Hub и выбранный SSH-сервер относятся к одной активной установке, и покажет текущие функции. Явно разрешите **удалённые команды**; затем при необходимости выберите PTY и файловый каталог `workspace`. Эти две функции в нынешнем Agent также требуют разрешения команд. Разовые команды доверенного администратора выполняются от пользователя Agent, а PTY — от отдельного `sovagrid-shell`, которому недоступен токен Agent. Новых ключей и токенов мастер не создаёт.

Нажмите «Проверить план», сверьте изменения и подтвердите отдельное применение. На время изменения Hub закрывает управление выбранным Agent и его relay-сеансы. Мастер устанавливает только принадлежащие ему ресурсы, перезапускает Agent, проверяет службы и согласует разрешение Hub с ревизией. Изменённый другим администратором план отклоняется. Выключение сохраняет пользовательские файлы и служебный SSH-туннель; VPN и журналы этим мастером не настраиваются.

Отмена или потерянный ответ не означают откат. Повторная проверка сверит обе машины и сохранённое намерение операции перед новым подтверждением. Старый журнал первоначальной установки и его пакет не меняются. Если runtime установленного Agent отличается от выбранного пакета, мастер потребует отдельного обновления вместо скрытой переустановки.

### Добавить другой сервер к центру мониторинга

После подключения к Hub нажмите **«Добавить другой сервер…»**. Укажите имя нового Ubuntu-сервера, его SSH-доступ, серверный пакет и IP Hub, доступный с этого сервера. Существующий профиль OpenSSH можно импортировать вместе с отдельным ключом промежуточного хоста. Мастер проверяет обе машины; перед изменениями показывает адреса, отпечаток Hub и хеш пакета. Затем нажмите «Установить Agent».

Для настройки нужен SSH root либо пользователь с `sudo -n`, а также логин администратора Hub. Токен Agent и ключ его постоянного соединения создаются на новом сервере автоматически. Connect передаёт Hub только хеш токена и открытый ключ. После первого измерения сервер появляется в общей панели; для дальнейшего сбора метрик держать Connect открытым не требуется. Команды, интерактивный терминал, файлы и VPN этим мастером не включаются.

При прерывании выберите сохранённую установку и повторите проверку. Можно указать перемещённый файл ключа или тот же серверный пакет; адреса сохранённой операции фиксированы. «Отменить и очистить» сверяет обе машины и регистрацию, прежде чем удалять принадлежащие операции данные. Уже приславший первое измерение Agent сохраняется. Для мастера нужны новые серверные компоненты с поддержкой удалённой установки; подробности и текущие ограничения — в [REMOTE_AGENT.md](https://github.com/sovagrid/sovagrid-blueprint/blob/main/REMOTE_AGENT.md).

### Первая установка через GUI

На **новом Ubuntu-сервере** заполните SSH-адрес, пользователя `root` и, если нужно, промежуточный хост и ключи. Нажмите «Подключиться»: если рядом с Connect есть проверенный серверный пакет Starter, приложение предложит установить backend и затем откроет панель. Для выбора другого локального пакета и функций нажмите «Установить на сервер…», отметьте нужные функции (WireGuard, терминал, файлы, журналы выбранных systemd-служб) и подтвердите установку. Для журналов впишите от 1 до 16 уникальных точных имён `.service`, по одному в строке, например `ssh.service`. Connect отклонит другие имена и старый пакет без защищённого journal broker ещё до SSH. Перед установкой Connect проверит архив и все SHA-256 из манифеста, покажет запросы SSH в отдельных окнах, отправит тот же проверенный архив через SSH и запустит `run.sh` от root. Прогресс показывается в окне; сырой вывод удалённой команды не показывается, чтобы случайно не раскрыть секреты. После ручной установки нажмите «Подключиться»: на обновлённом Hub вход в панель происходит по одноразовому SSH-пропуску; для старого Hub доступен вход в его локальную учётную запись.

Пакет создаётся из пяти серверных репозиториев организации SovaGrid скриптом `sovagrid-blueprint/package_server.py` и передаётся отдельно от сборки Connect. Проверка манифеста защищает от повреждения и опасных путей внутри архива, но **не подтверждает происхождение кода**: выбирайте только пакет из доверенного источника, поскольку его `run.sh` исполняется от root. Размер сжатого пакета ограничен 64 МиБ, общий размер файлов — 256 МиБ; ссылки, специальные файлы, дубли и неожиданные компоненты отклоняются. На сервере распаковка сначала идёт во временный каталог, а исходники перемещаются в `/opt/sovagrid-src` после проверки структуры. Уже установленный SovaGrid, существующий каталог исходников или занятые служебные пути приводят к отказу до передачи пакета. Обновление существующей установки через это действие не выполняется. Действие не включает управление Amnezia; остальные контейнеры не затрагиваются.

Первую установку сейчас можно запустить только через root SSH-вход на Ubuntu. Если провайдер допускает лишь пользователя с `sudo`, понадобится ручная первичная установка или отдельный поддерживаемый сценарий в будущей версии. На уже установленном сервере это действие ожидаемо откажет; используйте обычную кнопку подключения. Если `run.sh` завершится с ошибкой после начала установки, Connect сохранит исходники в `/opt/sovagrid-src` и сообщит о частичной установке вместо повторной попытки поверх неё.

### Функции на уже установленном сервере

Кнопка «Включить функции…» добавляет WireGuard, терминал, файловый раздел и/или журналы конкретных systemd-служб на хосте, где SovaGrid уже развёрнут с Agent. Сначала Connect выполняет **только чтение**: проверяет Ubuntu/root, root-owned исходники без символьных ссылок и права записи посторонних, маркеры управляемой установки, здоровый Hub/Web и активный Agent. Затем показывает действующие функции и отдельно спрашивает подтверждение выбранных. Для журналов форма принимает полный разрешённый список имён `.service`; он целиком заменяет старый, поэтому сохраняемые службы следует указать снова. Отдельный выбор «Полностью выключить журналы» снимает разрешение Agent, останавливает broker/socket и удаляет только управляемые файлы после своего подтверждения; он работает даже когда broker уже неисправен. Если всё уже включено либо выключение уже выполнено, сервер не изменяется. Перед записью проверки повторяются на сервере, после чего запускается только его существующий `/opt/sovagrid-src/sovagrid-blueprint/run.sh` с каноническими флагами. Старый `run.sh` без journal broker отклоняется до изменения сервера. `run.sh` пересобирает Hub/Web и перезапускает Agent, поэтому открытые сеансы могут прерваться. Ни токен, ни пароль в терминал вводить не нужно; SSH-авторизация происходит через графические окна. Исходники этой кнопкой не обновляются, управление Amnezia не включается. При неуправляемой или нездоровой установке Connect отказывает до запуска `run.sh`.

В том же мастере можно отдельно включить или выключить **только чтение списка Docker/Podman контейнеров**. Connect показывает действующее состояние и предупреждает, что серверный collector работает от root и получает доступ к сокету Engine. Перед применением он повторно сверяет установленный код, конфигурацию и выбранные функции; старый серверный пакет без поддержки inventory отклоняется. Клиент Connect не открывает Docker socket и не даёт этим переключателем право управлять контейнерами.

Журналы выдаются через отдельный Unix socket и пользователя `sovagrid-journal`, которому доступен только root-owned список служб. Сам `sovagrid` не включается в группы `systemd-journal` или `adm`, поэтому обычная команда Agent не получает общий доступ к журналу ОС. В Hub нужно отдельно разрешить удалённые команды для выбранного сервера. Подготовленный, но не применённый пакет обновления не включает journal broker.

### Управление разрешёнными системными службами

Кнопка **«Доступ к системным службам…»** открывает отдельный мастер для основного Agent и второго локального Agent собственного Hub. Сначала он по root/sudo SSH сверяет код установленного Agent с заранее проверенным манифестом серверного выпуска и без изменений читает состояние брокера. Затем можно выбрать службу из списка systemd или указать точное имя `.service`, разрешить для неё только нужные действия «Состояние», «Запуск», «Остановка», «Перезапуск» и проверить план. «Состояние» всегда включено: Hub требует свежую проверку того же unit перед изменением. Ограничение — 16 служб. Запись выполняет root-only серверный helper с проверкой ревизии; Connect передаёт политику через stdin, а не в командной строке. Выключение останавливает только socket выбранного брокера и оставляет список для последующего включения. Для локального Agent helper отдельно проверяет его конфигурацию и перезапускает только этот Agent, если добавляет socket.

Остановка `ssh.service` или сетевых служб может оборвать доступ к серверу; мастер показывает точный список действий перед подтверждением.

### Разрешения действий с Docker-контейнерами

Кнопка **«Действия с контейнерами…»** работает через тот же SSH-маршрут и root либо `sudo -n`. Сначала мастер сверяет установленный Agent с закреплённым серверным выпуском и показывает текущее состояние разрешений. Для выбора контейнеров нужен включённый сборщик: его root-owned снимок должен быть не старше двух минут, полным и совпадать по ID, имени и образу с прямым чтением Docker API. Поэтому на сервере без сборщика локальный Agent пока показывает только состояние разрешений: включение станет доступно после установки отдельного локального сборщика и обновления общего выпуска.

В список для выбора попадают только контейнеры, прошедшие те же проверки изоляции, что и серверный брокер Agent. Инфраструктура SovaGrid, Amnezia, VPN, SSH, Docker и сети, а также контейнеры с монтированиями, устройствами, дополнительными capabilities и общими пространствами имён исключаются. Для каждого точного ID, имени и ID образа можно отдельно разрешить состояние, запуск, остановку и перезапуск. Состояние обязательно. План и подтверждение показывают выбранные действия; данные передаются по stdin, без команд Docker или токенов в консоли.

Политика и отдельный маркер включения записываются в закрытый каталог выбранного Agent с правами root `0700/0600`. Если ответ SSH потерян, Connect пытается вернуть предыдущую политику; оставшуюся незавершённую операцию можно явно отменить кнопкой **«Восстановить прежнее»**. Кнопка **«Выключить»** удаляет маркер и сохраняет список для следующей настройки. Проверка состояния и выключение работают даже при временно недоступном Docker.

### Резервные копии Hub без консоли

Кнопка **«Резервные копии Hub…»** сверяет весь установленный исходный компонент Hub с манифестом серверного пакета, UID Hub и закрытые каталоги на выбранном SSH-хосте. После проверки можно посмотреть список снимков, проверить выбранный снимок или подтвердить создание нового. Создание сначала повторно сверяет список и код сервера, затем требует подтверждение, выполняет root-only команду и проверяет полученную копию. Если ответ потерян, копия могла появиться: мастер не повторяет создание автоматически и просит обновить список. В интерфейс попадают только UUID, время, размер и признак наличия токена; сам токен и содержимое базы остаются на сервере.

Копия содержит SQLite Hub и при наличии токен Telegram. Она **не** включает VPN-ключи, Caddy CA, настройки Agent и файлы сервера. После проверки копии кнопка **«Восстановить…»** показывает её точный UUID и дату. Подтверждённое действие через root/sudo SSH останавливает только контейнер Hub, делает страховочную копию текущих данных, применяет проверенный снимок, запускает Hub и ждёт его health-check. Старые сеансы, ожидающие команды и уведомления в восстановленной базе обезвреживаются. Если запуск не подтвердился, сервер пытается вернуть прежние данные; при дрейфе данных оставляет страховочную копию и явное состояние `recovery_required` для администратора. Повторять действие автоматически после потери ответа Connect не будет: кнопка состояния и история находят сохранённый запрос по UUID даже после перезапуска приложения. Для прерванного запроса кнопка **«Исправить сбой…»** отдельно подтверждает проверку серверного журнала и безопасное продолжение или возврат прежних данных. Токен и содержимое базы в GUI не передаются. Восстановление из копии с внешним Telegram-токеном либо с другим управляемым токеном сервер пока отклоняет. Мастер принимает только установленную точную версию закреплённого локального серверного пакета; на старой установленной версии запись заблокирована.

### Полные копии сервера

Кнопка **«Полные копии сервера…»** проверяет точный установленный серверный пакет по SHA-256 манифеста и каждого файла. Мастер показывает список закрытых архивов на выбранном SSH-сервере, проверяет хеш и структуру выбранного архива и даёт создать новый после явного подтверждения. В интерфейс попадают только ID, время UTC, тип установки, размер и количество объектов; пароли, VPN-ключи и сам архив остаются в root-only каталоге сервера. Потерянный ответ о создании считается неопределённым: мастер просит обновить список и не повторяет команду автоматически.

Для работающего сервера мастер показывает точный список управляемых служб и контейнеров, которые временно остановит серверный orchestrator. После подтверждения сервер записывает UUID задания в root-only журнал, останавливает только компоненты, участвующие в копии, создаёт архив и пытается запустить прежние компоненты. Внешний Agent и обратный SSH-туннель внешнего Agent не входят в этот план. Клиент сохраняет UUID, отпечаток SSH-маршрута и хеш проверенного пакета в закрытой локальной записи, показывает состояние задания даже после обрыва SSH и позволяет найти его в серверной истории после перезапуска приложения или на другом устройстве. Если worker завершился нештатно, отдельная кнопка после подтверждения просит сервер восстановить ранее остановленные компоненты; сервер откажет, пока worker работает. Архив при этом не создаётся повторно. Низкоуровневая offline-команда остаётся доступной только при уже остановленных записывающих компонентах. Восстановление полного узла из архива через GUI пока не поддерживается.

### VPN через графические мастера

**«Полный маршрут WireGuard…»** получает список только собственных управляемых VPN-инстансов, затем проверяет конкретный инстанс, точную установленную копию VPN-кода, наличие `nftables`, IPv4-пересылку и собственное NAT-правило. Включение и выключение передают свежую ревизию серверному root-only helper; при изменении состояния мастер требует повторной проверки. Другие firewall-цепочки и работоспособность выхода в Интернет этим статусом не подтверждаются: после импорта полного профиля проверьте внешний IP и доступность сайтов на телефоне. Серверный маршрут сейчас только IPv4; клиентский профиль включает `::/0`, чтобы IPv6 не уходил мимо VPN.

**«Управление Amnezia…»** позволяет выбрать AWG2 или WireGuard, посмотреть работающий контейнер и принять его для SovaGrid без ручного ввода Docker ID. Перед подтверждением мастер показывает полный ID контейнера и образа, хеши конфигурации и таблицы клиентов, порт, подсеть и число клиентов. Сервер повторно сверяет эти четыре значения при принятии; клиент не повторяет команду автоматически после потери ответа. Затем можно отдельно установить файлы broker, включить доступ к принятому контейнеру или снять разрешение. Перед каждым действием мастер заново сверяет источник, установленный код и состояние; принятие и установка broker не включают доступ автоматически. Подтверждение включения напоминает об окне обслуживания. Мастер не переписывает настройки Amnezia и не создаёт клиентские профили.

После принятия контейнера кнопка «Показать настройки» читает только его закреплённые параметры: интерфейс, адрес и подсеть, порт внутри контейнера, число собственных и внешних клиентов и, для AWG2, проверенные числовые поля конфигурации. Секретные ключи и данные клиентов не показываются. Обзор отдельно сообщает, что изменение этих параметров пока недоступно: для него потребуется безопасный перевыпуск клиентских профилей и миграция порта.

Для принятого AWG2 с полным набором AWG3 параметров кнопка «План AWG3…» открывает форму Jc/Jmin/Jmax, S1–S4 и H1–H4. Значения подставляются из прочитанной конфигурации; пользователь меняет их в графическом окне. «Проверить план» повторно сверяет контейнер и обзор, затем передаёт по root SSH только изменённые публичные числа вместе с точным SHA-256 конфигурации и поколением. Сервер строит предполагаемую конфигурацию в памяти и возвращает различия, её хеш и причины блокировки. Ни окно, ни серверная команда планирования не применяют настройки. При нуле клиентов и подтверждённых работающих параметрах план разрешает последующее применение в Web; при существующих клиентах показывает необходимость миграции их профилей. Ключи и содержимое клиентских профилей не передаются в Connect.

В том же мастере отдельная строка «Параметры AWG3» проверяет право изменения без записи. Кнопка «Разрешить изменение…» доступна только для принятого контейнера с нулём клиентов, работающим broker и подтверждёнными параметрами AWG3; она повторно сверяет состояние и просит отдельное подтверждение окна обслуживания. Разрешение действует только на числовые параметры без смены порта или ключей. Кнопка «Запретить изменение» снимает лишь это разрешение; контейнер, текущие настройки и профили остаются. Изменение конкретных чисел выполняется отдельно в Web после просмотра плана и одноразового подтверждения. Данные и служебные токены не нужно вводить в консоли.

Оба мастера закреплены за общим локальным серверным кандидатом и до установки его точной версии на целевом сервере не меняют состояние. Для полного маршрута на Ubuntu потребуется `nftables`. При его отсутствии отдельная кнопка после read-only проверки Ubuntu 22.04/24.04/26.04 и состояния пакета предлагает установить только эту зависимость через APT по подтверждённому root/sudo SSH. Мастер не запускает `nftables.service` и не записывает firewall-правила; после установки сверяет `nft --version` и выключенное состояние службы. Согласно [документации Ubuntu](https://documentation.ubuntu.com/security/security-features/network/firewall/nftables/), пакет поставляет службу выключенной по умолчанию. Если пакет или служба уже в необычном состоянии, автоматическая установка отказывается продолжать.

### Обновление существующего сервера через GUI

На **уже управляемом и исправном** Ubuntu-сервере нажмите «Обновить сервер…». Выберите доверенный `SovaGrid-server-source.tar.gz` или используйте пакет рядом с приложением. Connect локально проверит структуру, манифест и SHA-256 точной копии пакета, затем по SSH без изменений проверит root-owned исходники, манифест действующей версии, маркеры установки, Hub, веб-панель, Agent и включённые службы. Диалог покажет полный SHA-256, число файлов, текущие и новые commit ID пяти компонентов и действующие функции. После подтверждения Connect повторно проверит файл, передаст пакет и сверит SHA-256 на сервере до распаковки. Распакованные файлы дополнительно сверяются с манифестом и сохраняются в закрытом каталоге `/opt/sovagrid-candidates/<sha256>`.

При распаковке Connect сохраняет только разрешённые права архива: `0755` для каталогов, `0644` или `0755` для файлов и строго `0644` для Caddyfile. Сервер повторно проверяет права подготовленных исходников. Если пакет с тем же SHA-256 был подготовлен прежней версией Connect с неправильными правами, повторная подготовка откажет с ошибкой о занятом пути; администратору нужно убрать только повреждённый каталог этого digest и подготовить тот же пакет заново. Действующая версия при таком отказе не меняется.

После подготовки появляется отдельная кнопка **«Применить обновление»** с повторным подтверждением. Перед остановкой служб удалённый updater заново сверяет SHA-256 staged-архива, извлечённый манифест, путь и commit ID текущей установки, health Hub/Web/Agent, сервисы WireGuard/PTY/journal и точный список разрешённых журналов. Он сохраняет старые Docker image ID, root-owned исходники, настройки, управляемые systemd units, данные Hub/Caddy/VPN inventory, затем запускает новый `run.sh` с прежними флагами. Hub и Web останавливаются на время снимка. После установки проверяются контейнеры, HTTP/HTTPS, Agent, включённые sockets/timers, версии и флаги. При ошибке updater пытается восстановить резервную копию, старые образы и состояние служб; результат отката показывается отдельно. При прерывании следующая попытка сначала восстанавливает незаконченную операцию и требует нового предпросмотра.

Это **проверяемый откат SovaGrid-состояния, а не атомарная системная транзакция**. APT-пакеты, системные пользователи и возможные побочные действия стороннего кода не удаляются при откате. Записи, сделанные пользователями в новую версию между её запуском и провалившейся финальной проверкой, могут быть потеряны при восстановлении базы. Не запускайте параллельно ручной `run.sh` и другие root-операции над теми же путями. Если откат не прошёл health-check, копия остаётся в root-only `/opt/sovagrid-candidates/transactions/` для повторного восстановления и Connect не объявляет успех. Старые staged-кандидаты очищаются вручную; автоматической очистки пока нет. Пакет проверяется на целостность, но не подписан: происхождение подтверждайте доверенным способом. Commit ID выявляют одинаковую версию и изменение между предпросмотром и применением, но не доказывают хронологию релизов и не запрещают выбор старого пакета. SSH-пароль, ключ и 2FA вводятся через графические окна.

Если откат завершился и прошёл проверки, updater сохраняет только журнал неудачной установки в закрытом каталоге `/opt/sovagrid-candidates/failure-logs/` на сервере. Каждый файл создаётся как `root:root` с правами `0600`, содержит не более последних 2 МиБ вывода `run.sh`; хранятся не более пяти журналов. В GUI выводится только факт сохранения, без содержимого журнала: вывод установки может содержать секреты. Если журнал не удалось сохранить, об этом выводится отдельный безопасный статус. При неполном откате исходный журнал остаётся в закрытой транзакции вместе с резервной копией.

После подготовки можно выбрать **«Применить при простое»**. Connect сохранит закрытую локальную настройку только для выбранного SSH-маршрута, текущего манифеста сервера и точного SHA-256 одобренного пакета. Пока Connect открыт с этим сервером в форме и не держит панель подключённой, он проверяет разрешение каждые пять минут. Удалённый updater откладывает автоматическую попытку при действующем или недавно истёкшем сеансе Hub, незавершённом задании или ожидающем подтверждении Telegram; перед применением повторяет проверки пакета и версии, затем использует тот же резервный снимок и откат. После успешного применения это разовое разрешение выключается.

На сервере с новой версией `sovagrid-blueprint`, поддерживающей таймер, рядом есть отдельная кнопка **«Разрешить на сервере»**. Она передаёт через тот же проверенный root SSH-маршрут только SHA-256 уже подготовленного пакета и манифест действующей версии. Сервер сам повторяет проверку пакета, а затем примерно каждые 15 минут пробует выполнить обновление при простое; Connect можно закрыть. Разрешение действует для одного пакета не более 14 дней и снимается после успеха, ошибки или истечения срока. Кнопки «Состояние» и «Отключить» читают и снимают разрешение на выбранном сервере без консоли. Старый сервер без таймера покажет понятный отказ: сначала обновите его вручную. Включение серверного таймера выключает локальное разрешение Connect для этого SSH-профиля, если оно было сохранено.

Оба режима не ищут и не скачивают следующий релиз. Для непрерывного канала обновлений всё ещё нужны проверка происхождения будущих пакетов и режим Hub, приостанавливающий приём новых задач на время обновления. Проверка простоя сейчас не закрывает короткую гонку, если новое действие поступит сразу после неё.

Для быстрого запуска из папки есть `launch.cmd` на Windows и `launch.sh` на macOS/Linux (на Unix запустите `./launch.sh` в терминале). `launch.sh` выбирает системный Python, если у основного Python отсутствует Tkinter.

## Проверка ключа сервера

CLI использует `StrictHostKeyChecking yes` **и для целевого, и для промежуточного узла**. Неизвестный или изменившийся ключ прерывает подключение. GUI использует `StrictHostKeyChecking ask`: для нового ключа он показывает SHA256-отпечаток и требует явного подтверждения после сверки по независимому источнику. Изменившийся ключ OpenSSH отклоняет. Сначала получите отпечаток ключа из независимого доверенного источника, например из консоли провайдера или локальной консоли сервера:

```sh
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

В GUI при первом подключении сравните показанный отпечаток с полученным и подтвердите его в окне: OpenSSH добавит ключ в `known_hosts`. В CLI сравните отпечаток при обычном SSH-подключении и закрепите ключ там же до запуска Connect. Для маршрута через промежуточный узел отдельно проверьте его ключ и ключ целевого сервера (`[127.0.0.1]:2223` в `known_hosts`). Автоматического принятия нового ключа и отключения проверки нет.

## Создание нового SSH-ключа без терминала

В GUI рядом с приватным ключом сервера и ключом промежуточного хоста есть отдельная кнопка «Создать…». Выберите файл для новой пары Ed25519 и нажмите «Создать ключ». По умолчанию ключ защищается парольной фразой: OpenSSH запрашивает её и повтор в отдельных скрытых окнах, а Connect не получает эту фразу. При отмене или пустой фразе защищённый ключ не публикуется. Опцию можно явно выключить, чтобы создать ключ без фразы; текущий Apple-клиент импортирует только такой незашифрованный Ed25519.

Пара сохраняется только в выбранные локальные файлы: приватный ключ и соседний `.pub`. Существующие файлы, включая символические ссылки, не перезаписываются. Готовый приватный путь автоматически выбирается в исходном поле сервера или перехода; окно показывает SHA-256 fingerprint и позволяет копировать **только открытый ключ**. На сервер ничего не записывается. Для входа новым ключом добавьте его открытую часть в SSH-доступы через панель провайдера или администратора.

Перед сохранением пара создаётся и проверяется в закрытом временном каталоге на том же диске. Приватный файл имеет режим `0600` на macOS/Linux; на Windows staging ACL ограничивается текущим пользователем до генерации, и итоговый файл сохраняет этот ACL. Файлы публикуются готовыми через операции, отказывающие при занятом имени; при ошибке удаляются только созданные этой попыткой ссылки. Два имени файлов не являются общей транзакцией при внезапной потере питания. Каталоги/файловые системы без необходимых прав и поддержки безопасной публикации отклоняются. Создание и отмена выполняются вне потока интерфейса; для функции нужен системный `ssh-keygen`.

Формат проверяется по [OpenSSH PROTOCOL.key](https://github.com/openssh/openssh-portable/blob/master/PROTOCOL.key); создание пользовательских ключей Windows описано в [документации Microsoft](https://learn.microsoft.com/en-us/windows-server/administration/openssh/openssh_keymanagement).

## Что хранится и что нужно установить

Коннектор не сохраняет пароли и учётные данные Hub. Существующие SSH-ключи используются по выбранному пути; новая пара сохраняется только по явному действию в окне создания ключа. GUI передаёт SSH-ответы только по каналу stdout отдельного Askpass-процесса в OpenSSH: секреты не записываются в аргументы, переменные окружения, временный SSH-конфиг или журнал. Чтение начального пароля использует фиксированную команду `head -c 257 /etc/sovagrid/admin-password` и канал stdout второго SSH-процесса; пароль не добавляется в аргументы, окружение или лог. Временный файл конфигурации содержит только адреса, пользователей и пути к ключам; закрытый журнал запуска OpenSSH подтверждает готовность проброса. Оба файла удаляются при отключении. Ключи остаются у OpenSSH, Hub-сессия живёт в браузере. Скачанный установочный пакет хранится в закрытом временном каталоге (`0700`) как файл `0600` только до завершения установки, затем удаляется. Для подключения нужен работающий `ssh` в `PATH` (для создания ключей также `ssh-keygen`), Python 3.9+ и уже развёрнутая панель на целевом сервере. GUI также требует Tkinter.

Команда использует только локальный адрес `127.0.0.1`; при остановке SSH-процесса проброс исчезает. Если SSH завершился до ответа панели, проверьте ключи узлов, логин SSH, разрешение `AllowTcpForwarding` и работу SovaGrid Hub/Web на удалённом `127.0.0.1:8766`.

## Разработка и проверка

```sh
python3 -m unittest discover -s tests -v
```

Тесты проверяют валидацию адресов и учётных записей, строгую политику ключей для обоих узлов, работу с разными ключами, фактическое открытие и закрытие loopback-проброса тестовым SSH-процессом, контроль `/healthz`, отказ при изменении пакета между предварительным просмотром и передачей, отклонение сервером неверного SHA-256 и очистку конфигурации. Создание ключей дополнительно проверяется настоящим `ssh-keygen`: зашифрованная и незашифрованная пары, совпадение открытого ключа/fingerprint, отмена, отказ от перезаписи и гонка публикации. Тесты не обращаются к удалённым серверам.
